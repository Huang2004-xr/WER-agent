# 企业级开发约束

本文档是 WER Agent 的开发基线。代码、配置、接口、数据模型、Agent 行为和部署变更都必须按本文档执行。

## 1. 需求与范围

- 每个需求先写清业务目标、使用角色、验收条件和风险。
- 需求变更记录原因、影响范围、负责人和兼容策略。
- 新增 Agent 能力必须对应真实业务场景、输入、输出和失败处理。
- 高风险动作明确人工确认节点和拒绝后的处理路径。

## 2. 架构与模块边界

- 前端只依赖 `packages/shared` 的契约，不引用后端内部实现。
- 后端保持模块化单体，由 `app` 统一装配，不提前拆成微服务。
- `agent-runtime` 负责模型循环；`harness` 负责权限、预算、审批、恢复、取消、幂等和审计。
- `skill-runtime` 负责能力封装和注册；`workflow-runtime` 负责步骤编排、等待、重试和回退。
- 领域模块通过接口和端口通信；具体数据库、缓存、模型、队列和外部平台实现放在 `infrastructure`。
- 业务模块不直接操作 MySQL、Redis、文件系统或第三方 SDK。
- 当前正式运行基线为 PostgreSQL（权威数据）、Redis（缓存/锁/租约）和 BullMQ（长任务队列）；具体客户端只能出现在 `infrastructure` 适配器。
- 应用启动时必须校验正式基础设施配置；没有正式适配器时显式失败，不能隐式回退到内存状态。
- 新增跨模块依赖必须说明依赖方向、接口责任和测试边界。

## 3. 代码与类型

- TypeScript 使用严格模式，公共接口必须有明确类型。
- 一个模块保持单一职责，复杂逻辑拆成可独立测试的服务或纯函数。
- Controller、HTTP 路由和 Agent Loop 只负责协调，不承载全部业务逻辑。
- 错误使用统一错误类型，包含可追踪的错误码、用户提示和内部原因。
- 配置通过环境变量或配置适配器注入，不把环境差异写死在业务代码中。

## 4. API 与兼容性

- API 使用版本化路径，例如 `/api/v1/...`。
- 请求、响应和错误结构写入 `packages/shared`，前后端使用同一份契约。
- 长任务返回 `runId`，通过查询或流式接口获取状态，不让 HTTP 请求无限等待。
- 可重试接口使用幂等键；重复请求不会重复产生外部副作用。
- 已发布字段保持向后兼容，删除或修改字段必须经过迁移和版本评审。

## 5. 数据与隐私

- 核心数据明确所有者、访问范围、生命周期和删除策略。
- 用户、客户、策划资料和组织数据必须按租户/组织边界隔离。
- 数据库结构通过迁移脚本变更，并提供回滚或恢复方案。
- 重要状态支持版本、检查点、事件记录和恢复。
- 记忆记录来源、置信度、创建时间、更新时间和过期策略。
- 日志、Trace 和评测样本不得泄露密码、Token、完整客户隐私或无关敏感信息。

## 6. 安全与外部副作用

- 密钥、密码、Token 只从密钥管理服务或环境变量读取。
- Tool 调用必须通过权限、参数、预算、超时和副作用等级校验。
- 读操作和写操作分级；发布、发送、删除、提交报价、修改客户数据等写操作默认需要审批。
- 模型不能直接执行任意 SQL、Shell 或未注册的 HTTP 请求。
- 文件上传校验类型、大小、内容和访问权限。
- 所有 Agent Run 关联用户、会话、请求和操作记录。

## 7. Agent 专项治理

- 每次执行设置最大步数、Token/费用预算、总时限、单工具超时和重试次数。
- 支持取消、超时、失败恢复、断点续跑和幂等重放。
- Skill、Workflow 和 Tool 必须注册、校验、版本化并记录调用关系。
- 记忆写入必须区分工作记忆、事件记忆和长期事实，并支持人工纠正和删除。
- 每次模型决策、Skill 调用、Tool 调用、审批和状态迁移都产生审计事件。
- 评测至少覆盖事实性、安全性、工具选择、流程完成度、输出质量和异常恢复。

## 8. 测试与质量门禁

按改动范围选择并运行：

- 单元测试：模块内部逻辑和边界条件。
- 集成测试：模块协作、持久化和基础设施适配。
- API 测试：请求、响应、错误和兼容性。
- E2E 测试：策划人员的真实业务流程。
- Agent 回归评测：模型、Skill、Workflow 更新后的质量和安全变化。

当前项目的基础门禁：

```bash
pnpm typecheck
pnpm build
```

新增测试或评测脚本后，相关变更必须在合并前运行对应命令。

## 9. 可观测性与运维

每次执行至少关联以下标识：

```text
requestId
sessionId
runId
workflowId
skillId
toolCallId
```

系统必须能追踪请求来源、模型决策、工具调用、使用的记忆/知识、审批记录、失败步骤和最终输出。

- 开发、测试、预发布和生产环境隔离。
- 发布使用版本号、变更记录、灰度策略和快速回滚方案。
- 生产配置日志、指标、Trace、告警、备份和恢复演练。
- 队列任务具备租约、重试、死信和重复执行保护。

## 10. 提交与评审

- 提交格式统一为 `类型:中文描述`，类型和示例见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)。
- 一个提交只完成一个主要目的；无关格式化和业务改动分开提交。
- 合并前检查类型、构建、测试、权限、敏感数据、迁移和文档。
- 代码评审应重点检查行为变化、兼容性、数据安全、失败恢复和观测完整性。
